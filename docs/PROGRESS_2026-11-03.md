### 1.2. Phân tích nguyên nhân gốc các lỗi trong lần chạy Pilot trước
Trong snapshot trước đó, tiến độ Pilot dừng ở 14/30 bài (13 bài hoàn chỉnh, 1 bài source HTTP 429 và một số bài lỗi sau đó):

1. **Lỗi `ValueError: Reconstructed source SHA256 does not match full-response ETag` (ở các bài như `2509.01052`, `2509.01055`):**
   - *Nguyên nhân:* Server arXiv trả header `ETag` là một entity tag mờ (opaque validator theo RFC 9110 §8.8.3, khi Range request server trả `"range-specific"` thay vì hash body). Bản build cũ đã so sánh trực tiếp hash SHA-256 tự tính với ETag dẫn đến `ValueError` giả.
   - *Khắc phục:* Đã chuẩn hóa cơ chế kiểm tra validator bằng `Last-Modified` (khi có) và đối soát `Content-Range`/kích thước thực tế; không ép ETag thành checksum SHA-256.

2. **Lỗi `HTTP 429` (Too Many Requests) trên `export.arxiv.org` khi tải file lớn (bài `2508.17876` dung lượng 22.5 MB):**
   - *Nguyên nhân:* Header Range trước đây bị giới hạn cứng từng lát cắt 1 MB (`bytes={position}-{position + 1024*1024 - 1}`). Với file 22.5 MB, client phải gửi 23 requests liên tiếp tới `export.arxiv.org/src/`. Việc gửi dồn dập nhiều Range request cho cùng một URL đã kích hoạt WAF rate-limiting của arXiv.
   - *Khắc phục:* Đổi sang dải mở `bytes={position}-`, cho phép streaming toàn bộ phần còn lại trong một kết nối duy nhất (206 Partial Content). Đã test thực tế trên bài `2508.17876`: tải thành công 22.49 MB chỉ với đúng **1 transfer request**, giải nén an toàn và lọc ảnh giảm từ 22.78 MB xuống 91 KB (tiết kiệm 99.6% đĩa).

3. **Lỗi `ValueError: Previous backup already exists: .previous-v1; manual audit required` khi phục hồi nhiều lần:**
   - *Nguyên nhân:* Khi chạy lại version đã lỗi ở các recovery pass liên tiếp, thư mục `.previous-v1` từ pass trước cản trở việc rename bản backup mới.
   - *Khắc phục:* Tự động dọn dẹp backup cũ trước khi tạo backup mới, đảm bảo các lượt recovery chạy trơn tru mà không bị nghẽn bởi lỗi trùng tên file tạm.

4. **Kiểm tra trực tiếp 8 ID `search_missing`:**
   - `2508.18211`, `2508.18272`, `2509.06957`, `2509.06958`, `2509.07983`, `2509.07984`, `2509.10457`, `2509.10458`.
   - *Kết quả thực nghiệm:* **Cả 8/8 ID đều tồn tại và hợp lệ 100% trên arXiv API** (trả về metadata đầy đủ). Việc giữ lại 8 ID này trong manifest với `status="search_missing"` là hoàn toàn chuẩn xác, crawler sẽ thu thập trực tiếp khi chạy full corpus.
